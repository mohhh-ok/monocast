# error-investigate

エラー調査スキル。**起点は必ずログ**。ログを見ずに「たぶんあそこのコードでは…」と推測から入らない。ログで事実を確定してから、必要ならコードを追う。

理由：エラー調査は推測ベースで進めると的外れになりがち。実際にプロセスが何を吐いたかが一番強い手がかりなので、まずログを読み、tag と msg を見て、初めて「どのモジュールを開けば良いか」が決まる。

## 動作

### 1. ログファイルを探す

優先順位：

1. `.logs/app.jsonl`（このリポジトリの JSONL ログ）
2. `logs/*.log`, `*.log`（プロジェクト直下）
3. `~/Library/Logs/` 配下（macOS アプリログを聞かれた場合のみ）

見つからなければ「ログファイルが見つかりません。`.logs/app.jsonl` などのパスを教えてください」と返して終了。勝手に作らない。

### 2. レコードを抽出する

JSONL なら `jq` で `level` が `error` または `warn` の行を取り出す。直近のものを優先。デフォルトは最新 50 件。

```bash
tail -n 2000 .logs/app.jsonl | jq -c 'select(.level=="error" or .level=="warn")' | tail -n 50
```

プレーンテキストログなら `grep -iE 'error|warn|exception|failed|fatal'` で拾う。

ユーザーが「今日のだけ」「直近1時間」など期間を指定したら `ts` フィールドで絞る。指定がなければ全期間から末尾 50 件。

### 3. ログ要約を出す

最初の応答では、必ずこの形でログ事実だけを先に提示する。コード調査・原因推測は **このステップでは混ぜない**。理由：ユーザーがログだけ見たい場面で、推測まで一緒に流れてくると焦点がぼやけるから。

```
## ログ要約

参照ファイル: <パス>
抽出件数: <error N件 / warn M件>
期間: <最古 ts> 〜 <最新 ts>

### error
- [<ts>] [<tag>] <msg>  (+ extra フィールドがあれば inline で)
- ...

### warn
- [<ts>] [<tag>] <msg>
- ...
```

件数が多すぎる（>20件）なら、同じ `tag` + `msg` をまとめて「N回」とカウント。スタックトレースなど長いフィールドは 1〜2 行に省略する。

### 4. コードを追って原因を特定する

ログ要約を出したら、続けて原因調査に進む。次の手順で：

1. **エラーの tag・msg から該当箇所を特定** — `tag` はモジュール名（例: `news.rss`, `tts.voicevox`）に対応していることが多い。`grep -rn "<msg のキーワード>" src/` でログ出力箇所を特定し、そこから上流に遡る。
2. **extra フィールドを手がかりに使う** — `url`, `durationMs`, `error`（外部APIの生エラー）など。例えば `error: "ETIMEDOUT"` ならネットワーク層、`error: "ZodError"` ならスキーマ不整合、というように切り分ける。
3. **原因と「ログから読み取れる範囲」を区別して報告する** — 「ログ上の事実」「コードから読み取った挙動」「推測」を混ぜない。推測する場合は「推測：」と明示する。

ログだけで自明な場合（例：単純なネットワークタイムアウトが1回だけ）は、コード調査をスキップして「これだけのようです」で終わってよい。深掘りが要らない事象まで毎回コードを開くと冗長になる。

### 5. 修正提案はユーザーが求めたら

「これ直せる？」と聞かれて初めて、具体的な修正案を出す。ログ要約 → 原因報告までで止めて、自動で修正パッチまで書き始めない。理由：エラー調査と修正は別フェーズで、原因特定の時点でユーザーが「どう直すか」を判断したいことが多いため。

## ログ形式の参考（monocast 系プロジェクト）

`.logs/app.jsonl` の各行は `src/lib/log.ts` で書かれた JSON：

```json
{"ts":"2026-05-12T10:23:45.123+09:00","level":"error","tag":"news.rss","msg":"feed fetch failed","url":"https://...","error":"ETIMEDOUT"}
```

- `ts`: ISO8601（タイムゾーン付き）
- `level`: `debug` / `info` / `warn` / `error`
- `tag`: モジュール名（`news.rss`, `tts.voicevox` など）。コード上の `log.error("news.rss", ...)` を `grep` すれば呼び出し元を辿れる
- `msg`: 短い説明
- 任意の追加フィールド: `url`, `error`, `durationMs` など

`debug` / `info` はノイズになるので、明示的に求められない限り出さない。

## 禁止

- ログを読まずに推測ベースで原因を語る
- ログを書き換える・削除する
- 求められていない修正パッチを勝手に書き始める
