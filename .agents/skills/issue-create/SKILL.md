# issue-create — GitHub Issue 起票スキル

ユーザーへの質問を最小回数で進めて、抜け漏れのない Issue を作る。`gh issue create` 実行までを 1 セッションでやり切る。

## 使うべきタイミング

- `/issue-create` と打たれた
- 「Issue を立てたい」「チケット起票して」「issue 作って」「バグ報告したい」「機能要望出したい」
- 「これ Issue 化しといて」のように文脈で起票を求めている
- ユーザーが背景説明をしながら「あとで起票しておきたい」旨を述べた場合も提案する

## 使ってはいけないタイミング

- 既存 Issue を読み込みたい → `issue-pick` スキル
- Issue へのコメント追加・既存 Issue の更新・クローズ（このスキルの責務外）
- PR の作成（`gh pr create` は別途）

## 前提チェックはしない

`gh auth status` / `gh repo view` / `gh label list` の **事前チェックは行わない**。普段はほぼ常に成功するため、毎回叩くと会話のノイズになる。代わりに **遅延検知** で対応する: 最終的な `gh issue create` を実行したときだけ失敗を検出し、エラー内容から原因を特定して案内する（後述「Step 6: 起票実行」「エラー時の対応」を参照）。

ただし、起票直前に **対象リポジトリだけは一度確認** する: `gh repo view --json nameWithOwner -q .nameWithOwner` で得た値を「`<owner/repo>` に Issue を作ります。よろしいですか？」と短く確認。違うリポジトリにしたい場合は `gh issue create --repo <owner/repo>` で指定する。

## 対話フロー

### Step 1: 概要のヒアリング

最初の質問はこれだけ。

> **どんな Issue を立てますか？1〜2 文で内容を教えてください。**

ユーザーの回答を受けて、内部で **type を自動判断** する（次節「type 自動判断ルール」参照）。判断結果は Step 4 の確認時にユーザーへ提示するが、この時点では聞き返さない。

### Step 2: 詳細ヒアリング（type で分岐）

ユーザーが Step 1 で既に答えている項目はスキップする。質問は 1 つずつ、または 2〜3 個まとめて出して構わない。**ユーザーが疲れない程度の最小回数** に抑え、AI が常識で埋められる項目は質問しない。

#### 推定 type が `fix`（バグ）の場合

1. **再現手順** を箇条書きで（1, 2, 3 …）
2. **期待挙動** を 1〜2 文で
3. **実際の挙動** を 1〜2 文で
4. **環境・補足**（ブラウザ・OS・ロール・データ条件・URL など。任意）

#### それ以外（feat / refactor / chore / docs / question / other）の場合

1. **背景・課題**（なぜこれをやりたいのか。1〜3 文）
2. **やること**（箇条書き 2〜5 項目）
3. **やらないこと**（スコープ外。任意）
4. **受け入れ条件**（検証可能な形のチェックボックス 2〜4 項目。任意）

### Step 3: priority のヒアリング

```
優先度を選んでください。
- high: 業務が止まる / 顧客影響 / リリース直前
- mid : 通常の改善・機能追加（デフォルト）
- low : 思いつき・やれたらやる
```

未回答なら `mid` を採用する。リポジトリに priority ラベル運用が無い場合、Step 6 のラベル付与で外せばよいので、ここでは聞いておく。

### Step 4: ドラフト生成と確認

タイトルと本文を以下のフォーマットで組み立て、**コードブロックで全文をユーザーに見せて** 確認する。

#### タイトル

- 形式: `<機能名や領域>: <何をやるか>`
- 言語: 日本語（リポジトリ慣習が英語ならそれに合わせる）
- 文字数: **70 文字以内**
- 例: `chore: docker-compose で PostgreSQL を立てるローカル開発環境を整備`

#### 本文（バグ以外）

```markdown
## 背景・課題

<Step 2 で得た背景>

## やること

- <項目 1>
- <項目 2>

## やらないこと

- <スコープ外。無ければセクションごと省略>

## 受け入れ条件

- [ ] <検証可能な条件 1>
- [ ] <検証可能な条件 2>
```

#### 本文（バグ）

```markdown
## 再現手順

1. <手順 1>
2. <手順 2>

## 期待挙動

<期待されること>

## 実際の挙動

<実際に起きていること>

## 環境・補足

<必要なら。なければセクションごと省略>
```

#### 確認時のメッセージ例

> 以下の内容で起票します。
>
> **リポジトリ**: `<owner/repo>`
> **タイトル**: `<title>`
> **ラベル**: `type:<x>`, `priority:<y>`
>
> ```markdown
> <body>
> ```
>
> このまま起票しますか？（yes / 修正したい部分を指示 / cancel）

確認前に **本文をざっと見て**、パスワード・トークン・APIキー・メールアドレス等の個人情報や秘密情報が含まれていそうなら注意喚起する。

### Step 5: 修正ループ

ユーザーが修正を指示した場合、該当部分だけ書き直して **Step 4 の確認に戻る**。タイトル・ラベル・本文のいずれも書き換え可。

### Step 6: 起票実行

ユーザーが `yes` と答えたら、以下のコマンドで起票する。

```bash
gh issue create \
  --title "<title>" \
  --body "<body>" \
  --label "type:<x>" \
  --label "priority:<y>"
```

- `--assignee` は付けない（着手するときに assign する運用が一般的）
- 別リポジトリ指定が必要な場合は `--repo <owner/repo>` を追加

成功したら `gh issue create` が返した URL を **そのまま提示** してフロー終了。

### エラー時の対応（遅延検知）

`gh issue create` の stderr を見て原因ごとに分岐する。

- **ラベルが存在しないことによる失敗**（例: `could not add label: 'type:chore' not found`）
  → 「`type:*` / `priority:*` ラベルがリポジトリに未整備です。どうしますか？」と確認し、以下から選んでもらう:
  - **A. 標準ラベルを作成して再起票** → 不足分のみ下表に従って `gh label create` で作成し、同じ Issue を再度 `gh issue create` で起票
  - **B. ラベル無しで起票** → `--label` を全て外して再実行
  - **C. 近いラベル名を使う** → `gh label list` で確認してからラベルを差し替えて再実行

- **認証エラー**（`gh auth status` 系のメッセージ）
  → 「`gh auth login` を実行してから再度 `/issue-create` を起動してください」と案内して終了。**この場合ドラフト本文は会話に残しておく** ので、ユーザーが再実行時に貼り直せる

- **GitHub リモート未設定 / repo not found**
  → 状況をそのまま伝えて終了。`--repo` 指定の打ち直しを提案してよい

- **`gh: command not found`**
  → `gh` のインストール（`brew install gh` など）を案内して終了

- **その他の失敗**
  → stderr をそのまま提示し、ユーザーの判断を仰ぐ

- **どの段階でも `cancel`**
  → 何も起票せず終了。ドラフトの保存は行わない

#### 標準ラベル作成時の色・説明

リポジトリに `type:*` / `priority:*` 運用が無く、新規に作る場合のテンプレート。

| ラベル | 色 | 説明 |
|---|---|---|
| `type:feat` | `#a2eeef` | 新機能・機能追加 |
| `type:fix` | `#d73a4a` | バグ修正 |
| `type:refactor` | `#fbca04` | 挙動変更を伴わない構造変更 |
| `type:chore` | `#cccccc` | 依存更新・設定・ビルド・スクリプト |
| `type:docs` | `#0075ca` | ドキュメントのみ |
| `priority:high` | `#b60205` | 高優先度 |
| `priority:mid` | `#fbca04` | 中優先度 |
| `priority:low` | `#bfdadc` | 低優先度 |

作成コマンドの例: `gh label create "type:feat" --color "a2eeef" --description "新機能・機能追加"`

## type 自動判断ルール

Step 1 のユーザー回答に対し、以下のキーワード/文脈シグナルから type を 1 つ選ぶ。複数該当する場合は **上から優先**（fix が最優先）。

| シグナル | type |
|---|---|
| 「バグ」「動かない」「壊れている」「再現」「エラーが出る」「直したい」 | `type:fix` |
| 「新機能」「追加したい」「実装したい」「作りたい」「〜画面が欲しい」 | `type:feat` |
| 「リファクタ」「整理」「挙動は変えない」「分割したい」「責務」 | `type:refactor` |
| 「依存更新」「設定」「ビルド」「CI」「Docker」「スクリプト」「環境構築」「lint」 | `type:chore` |
| 「README」「ドキュメント」「手順書」「ガイド」「説明を書く」 | `type:docs` |
| 「質問」「教えて」「相談」 | `type:question`（運用に無ければ `type:chore` か無ラベル） |

判断に迷う場合は **`type:chore` をデフォルト** とし、Step 4 の確認時にユーザーへ別案を提示する。

## 守るべきこと

- **質問は最小限**に。ユーザーが既に話した内容を聞き返さない
- ドラフト全文を確認させずに起票しない
- 起票時に `--assignee` は付けない
- Issue 本文の言語は **日本語**（リポジトリ慣習が英語ならそれに合わせる）
- ラベルの事前チェックはしない（失敗してから対応）
- 失敗ケースでは stderr を隠さず提示
- 派生して別 Issue が必要だと気づいた場合、本フロー終了後にユーザーへ「この派生分も別 Issue にしますか？」と提案してよい
- スクリーンショットや画像を添付したいとユーザーが言った場合、`gh issue create` ではアップロードできないので、起票後に Web から添付するよう案内する
- タイトルが既存 Issue と被りそうな場合（明らかに似たキーワードがある等）、`gh issue list --search "<keyword>"` で重複チェックを提案してよい

## やらないこと

- PR の作成
- Issue へのコメント追加・既存 Issue の更新
- マイルストーン / プロジェクト / Discussions の操作
- Issue のクローズ
- assignee の付与
